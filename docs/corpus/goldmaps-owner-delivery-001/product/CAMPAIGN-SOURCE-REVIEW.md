**Disposition:** The reviewed assembly, qualification and publication flow is

executed policy checks, not a Windows execution or downloadable-artifact pass.

Specialist B (`/root/product`) reviewed the integration lead's
`run_campaign.py`, `seal_payload.py` and `goldmaps-owner-delivery.yml`. This

## Source custody and counts

The workflow checks out the exact delivery SHA and the separate accepted engine
`00cdb02f103265b6dc5224c68283e9a0c8cb449f`, preserves source line endings, and
stages only source-verified runtime files and materialized native dependencies.
The frozen scientific engine remains separately identified. The seal verifies
product source bytes against the requested commit, records all immutable files,
and excludes portable user data and generated Godot caches from publication.

Required and optional campaigns are serial within one hosted Windows job. Their
exact engine, Godot and native-probe identities must agree, and overlapping
Setup digests are rejected. The merged matrix counts logical aliases separately
from distinct payloads and preserves refused originals and unqualified cases.
Per-variant native receipts are rehashed and joined by exact Setup digest; byte
aliases share execution evidence without sharing owner decisions.

## Actual launcher and artifact path

The pipeline reseals after adding immutable evidence, before the next browser
launch. It exercises the actual one-click launcher with an explicit headless QA
switch, then requests separately labelled hosted graphical captures. The final
ZIP is checked independently, reconstructed from its exact acquisition manifest,
freshly extracted to a path containing spaces, and run through actual launcher,
paint/save/reopen and post-execution integrity checks. The reconstruction check
does not pretend to be an execution check.

Only a successful campaign publishes the playable artifact. The artifact
contains the named inner Windows ZIP plus its checksums and reconstruction
inputs; a separate always-uploaded evidence artifact preserves failures. The
workflow uses pinned Actions, read-only repository permissions, no release step,
no merge step, no owner-data upload and 90-day artifact retention. Its dedicated
concurrency group does not cancel other programmes.

## Finding resolved

The initial graphical integration accepted a nonzero graphical process whenever
`product_defect` was missing or false. That could have hidden a driver failure.
The lead corrected it: timeout or a missing/true defect field now fails; a
nonzero result is allowed only with an explicit recognized native Windows
display limitation; exit zero requires the complete planned-case status.

The rendered driver still reports capture scope, renderer and dimensions rather
than visual quality acceptance. Actual images require independent inspection,
and physical Windows/NVIDIA feel, subjective route judgement and all final
classifications remain owner-dependent.
